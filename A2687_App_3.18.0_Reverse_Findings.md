# Anker App 3.18.0 — A2687 reverse-engineering findings

## Input

- APK: `com.anker.charging_3.18.0.apk`
- Size: `361233376` bytes
- SHA-256: `4737B82D11F4819AD0249B526FB486AA2D3FAB8308804E03F2C8B2864FE74236`
- Flutter/Dart: Dart `3.4.4`, Android ARM64, compressed pointers, null safety

## Confirmed architecture

The A2687 business code is implemented in Flutter AOT code inside `libapp.so`.
It does not construct BLE packets directly. The confirmed call chain is:

```text
A2687 UI / service
  -> AKIotA2687Command
  -> KitExtension.handle("akiot.device.invoke_action", request)
  -> AkIotKitFlutter.handle(identifier, param)
  -> Flutter MethodChannel "ak_iot_kit_flutter", method "handle"
  -> protected Android AK IoT Kit implementation
  -> BLE framing, authentication, encryption and GATT transport
```

Recovered Dart source paths include:

- `package:charging/ak_iot_kit/business/A2687/command/a2687_command.dart`
- `package:charging/ak_iot_kit/business/A2687/model/a2687_device_info.dart`
- `package:charging/ak_iot_kit/business/A2687/service/a2687_device_info_service.dart`
- `package:charging/ui/page/device/a2687/...`
- `package:ak_iot_kit_flutter/src/ak_iot_kit_flutter.dart`

The Flutter platform channel name is confirmed as `ak_iot_kit_flutter`.
Calls use channel method `handle` with a map containing `identifier` and `param`.

## A2687 and A17A5 are separate implementations

The App contains both:

- A2687 code under `business/A2687`, `model/a2687` and `ui/page/device/a2687`
- A17A5 code under `ble/device/A17A0/a17a5_anker_device.dart` and A17A5-specific assets

Therefore the existing WebBLE project's `A17A5_*` naming should not be treated as
proof that A2687 uses the A17A5 implementation. It is most likely historical naming
from the earlier packet-hooking work.

The App/SDK command enum also maps the settings shown on the A2687 settings

The screen-lock enum is `0=30 seconds`, `1=1 minute`, `2=5 minutes`,

`2=Japanese`, `3=German`. Direction is `0=up`, `1=left`, `2=down`,
`3=right`. These single-value settings use the same typed one-byte `A2`
layout as the confirmed mode/fixed-setting actions.

The charging-mode values used by the A2687 UI are:

| `chargingProtocol` | Meaning |
| --- | --- |
| `0` | intelligent / AI mode |
| `1` | standard mode |
| `4` | custom mode |

The fixed-allocation page uses two profile values:

| `fixedAllocation` | Meaning |
| --- | --- |
| `0` | dual-laptop allocation |
| `1` | C1-priority allocation |

For custom mode, the App sets `chargingProtocol = 4` and sends:

```text
customChargingProtocolPower: 5 integer values
customChargingProtocol:      9 integer values
```

The five-value power array is now mapped end-to-end from the cloud custom-mode
model through `A2687CustomChargeEditLogic` into `setCustomChargeModeParams`:

```text
[profile number, auto-exit flag, C1 power, C2 power, C3 power]
```

The auto-exit boolean is serialized as `0` or `1`. The official A2687 editor
sets a maximum of `140 W` for each individual C port and a maximum total of
`160 W`. Its critical-range helper treats port power as either `0 W` or at
least `15 W`, so WebBLE validates each port as `0` or `15..140 W` and rejects a
sum above `160 W`.

The nine-value protocol array is three 3-byte records, one for each of C1, C2
and C3. The current App builds each record as `[mask, 0, 0]`. The first-byte mask
has been recovered from the Flutter implementation:

| Bit | Mask | Protocol |
| --- | --- | --- |
| 0 | `0x01` | SCP |
| 1 | `0x02` | UFCS |
| 2 | `0x04` | PD 12 V |
| 3 | `0x08` | PPS 5-11 V |
| 4 | `0x10` | PPS 5-16 V |
| 5 | `0x20` | PPS 4.5-21 V |
| 6-7 | `0x40` / `0x80` | reserved/unused by this UI |

### Official App's 3-of-4 PD/PPS check

Before enabling a protocol, `CustomProtocolManagerLogic` counts only these
four items: PD 12 V, PPS 5-11 V, PPS 5-16 V and PPS 4.5-21 V. It blocks the
next item when that count is already `>= 3`. SCP and UFCS are excluded, which
is why the official UI reaches at most `5/6` enabled protocols.

No account, subscription, entitlement or license check is involved in this
path. It is an App-side protocol-combination rule. That proves the `5/6` UI is
not an authorization limit, but does not prove that firmware will accept or
advertise all four PD/PPS profiles simultaneously.

The App enforces this twice: `isProtocolDisabled()` greys the remaining
unchecked special item when the count reaches three, and `toggleProtocol()`
checks again before changing state and shows `platformChargingProtocolLimitTips`
if the user attempts the fourth item. Already-enabled special items remain
available so one can be turned off; UFCS and SCP are never disabled by this
count. WebBLE now mirrors that behavior and defaults to `5/6` (`0x3B`, PD 12 V
off) instead of allowing mask `0x3F` through this UI.

### Standalone Protocol Management save path

The screenshot's standalone page is not the same write path as custom charging
mode `0x0206/A4`. The App:

1. fetches the per-port model from
   `/mini_power/v1/app/setting/get_port_protocol_status`;
2. edits grouped protocol `name`/`status` values independently for each port;
3. supports saving the current port or applying it to all ports;
4. receives a per-port integer `tlv` list from the cloud model;
5. calls `action_set_protocol_switch` with that list as `protocolSwitchData`.

The local action maps to the SDK's separate `0x021D` command. Because the byte
list is supplied by the cloud response rather than constructed in Flutter, the
standalone `0x021D` TLV layout cannot safely be replaced with the custom-mode
bitmask without a real response/cache capture. The WebBLE UI therefore applies
the official selection rule to its custom-mode masks but does not claim that
`0x0206/A4` is the standalone Protocol Management command.

The laboratory-protocol UI independently uses bit 0 for SCP, bit 1 for UFCS,
and bits 2-4 for the same three PPS ranges. That command can update AI-mode and
standard-mode protocol masks separately.

The action order and the SDK's typed-value convention strongly support the
following request layout:

```text
0x0205 fixed allocation
  A1 = 21
  A2 = 01 <fixedAllocation>
  FE = timestamp

0x0206 intelligent/standard mode
  A1 = 21
  A2 = 01 <chargingProtocol>
  FE = timestamp

0x0206 custom mode
  A1 = 21
  A2 = 01 04
  A3 = 04 <five custom-power bytes>
  A4 = 04 <nine protocol bytes>
  FE = timestamp
```

Here `01` is the one-byte integer wrapper already confirmed by `0x0207`, and
`04` is the raw byte-array wrapper already used by the official A17A5/A2687
transactions for byte lists and structures. The native action serializer is
VMP-protected, so the custom array wrapper remains a high-confidence inference
rather than a captured official `0x0206` packet. WebBLE therefore exposes the
single-value `0x0205` and `0x0206` writes normally, while custom power/protocol
sending is gated behind an explicit experimental unlock and confirmation.

## APK protection boundary

Direct JADX decompilation of the APK produces only the `s.h.e.l.l` loader classes.
The real Android implementation of the `ak_iot_kit_flutter` channel is loaded at
runtime and is not present as ordinary, statically readable DEX in the APK.

The `classes.dex` through `classes10.dex` files currently located in the desktop
`Jadx` directory belong to an unrelated Tencent application and must not be used
for this project.

Searching all packaged ARM64 native libraries found the A2687/action/channel strings
only in Flutter's `libapp.so`, which is why the runtime DEX recovery described below
was required.

## Runtime DEX recovery completed

The MuMu emulator is rooted successfully (`su -c id` returns UID 0). A matching
Frida 17.16.3 server was installed in the emulator and attached to
`com.anker.charging`.

The runtime dump recovered 34 DEX images. After repairing their in-memory DEX
checksums, JADX produced approximately 32,210 Java files, including 1,017 files
under the official `com.anker.akiotkit` package.

The most important recovered packages are:

- `com.anker.akiotkit.infrastructure.akble`
- `com.anker.akiotkit.bizcore.support.cmd`
- `com.anker.akiotkit.bizcore.services.pairing.bind`
- `com.anker.akiotkit.bizcore.services.device.sub_services`

The APK uses an iJiami/爱加密 VMP layer. Selected method bodies are replaced in
the DEX by an immediate `return` followed by NOPs and are executed by the unpacked
`libexec_x86.so` runtime instead. Although those methods cannot be read normally
by JADX, they can still be instantiated and executed inside the rooted emulator.

## Official charging BLE framing constants

`ChargingBleGenerator` exposes the following protocol constants:

- packet prefix: `FF 09`
- protocol version: `03`
- slave ID: `00`
- encrypted feature bit: `0x40`
- opcode length: 2 bytes
- payload length field: 2 bytes
- checksum length: 1 byte
- GCM associated data:
  `33 22 11 00 77 66 55 44 BB AA 99 88 FF EE DD CC`

The GCM AAD is byte-for-byte identical to the value already present in the
WebBLE project.

The official command enums identify A2687/minicharge port control as:

- request `minicharge_SetPortSwitch`: decimal `519`, hex `0x0207`
- response `minicharge_PortSwitch`: decimal `2567`, hex `0x0A07`

The response high byte contains the response/ACK bit; after the existing parser
masks that bit, it appears as `0x0207`. Therefore the project's selected port
switch opcode is correct, although its `A17A5_*` name is misleading.

### Confirmed WebBLE handshake defects

The current project sends `A3` for command `0x0022` as:

```text
04 80 8F FF FF
```

The official generator's `A3` data is only:

```text
80 8F FF FF
```

The leading `04` is the TLV length seen in a decoded packet, not part of the
value. `buildTlvBuffer()` already writes the length, so the current WebBLE code
adds one byte too many.

The official `0x0027` generator also includes `A3 = password`; the current
WebBLE sequence sends only `A2`. This is another incomplete part of the captured
authentication flow.

## Confirmed ECDH behavior

`AesUtil_androidKt.getClientPublicKey()` returns a 65-byte SEC1 uncompressed
P-256 public key encoded as 130 hexadecimal characters:

```text
04 || X (32 bytes) || Y (32 bytes)
```

`GCMPubilcKeyCmd` removes the leading `04` and sends the remaining 64 bytes as
TLV `A1` in command `0x0021`.

`computeEcdhWithPublicKey()` returns a 32-byte ECDH shared secret (64 hexadecimal
characters). Consequently, the hard-coded 64-byte `0x0021` blob in WebBLE is a
captured public key, not a reusable session secret. Without the corresponding
private key, the browser cannot reproduce the official ECDH exchange.

The compatible open-source SolixBLE implementation confirms the direct session
split used after `0x0021`:

```text
AES-128 key = sharedSecret[0:16]
GCM nonce   = sharedSecret[16:28]
AAD         = 33 22 11 00 77 66 55 44 BB AA 99 88 FF EE DD CC
```

No additional KDF or `0x0022` response transform is required for the session
key. WebBLE now generates a fresh WebCrypto P-256 key pair on every connection,
sends `X || Y` in `0x0021/A1`, imports the device's returned point, derives the
32-byte secret, and switches to the split above before sending `0x0022`.

### Temperature result

There is no temperature field in the official A2687 `A2687DeviceInfo` model.
There is also no temperature field in the dedicated port-history model
`charging/model/a2687/a2687_port_detail_data.dart`. A search of the complete
A2687 business/UI implementation finds no A2687 temperature value being parsed
or displayed, even though other Anker product models in the same app do have
explicit temperature fields.

The app does, however, expose a qualitative thermal-protection state through
the A2687 `errorCode` path. `MsgCodeContent.a2687CodeMap` covers the device-error
range `1..63` and reduces it to two official messages:

- `a91b2Error1`: abnormal device temperature detected; over-temperature
  protection will be enabled
- `a91b2Error2`: port abnormality detected; remove the connected device

The Simplified Chinese translation for the first message is
`故障1: 检测到设备温度异常，将启用过温保护。` This matches the charger's
non-numeric temperature/protection indication much better than a Celsius
telemetry field.

Therefore app version 3.18.0 supports a qualitative result such as
`normal / over-temperature protection / port fault`, but it does not provide
evidence that A2687 exposes a numeric temperature through its supported app
API. An undocumented raw sensor value may still exist, but it cannot be labelled
as Celsius without a real-device capture showing that it tracks heating and
cooling.

## Additional official A2687/minicharge interfaces

The official request/response enums expose the following important read path:

| Purpose | Request | Response |
| --- | --- | --- |
| all device information | `0x0200` | `0x0A00` |
| port detail/history data | `0x020C` | `0x0A0C` |

The Flutter action for `0x020C` is named `prop_read_port_detail_data`. Its
response model contains:

- `sendStatus`
- `packageNumber`
- `packageTotalNumber`
- C1/C2/C3 history voltage arrays
- C1/C2/C3 history current arrays

The app uses those arrays to build the per-port voltage, current and calculated
power curves. This is the most promising additional read interface to add after
the normal realtime snapshot.

The curve conversion code also establishes the sample units:

- voltage samples are millivolts and are divided by `1000`
- current samples are milliamps and are divided by `1000`
- `65535` (`0xFFFF`) is the missing/invalid sample sentinel
- the app rounds voltage and current down to one decimal place
- power is calculated as `voltage * current` and rounded down to one decimal
  place

The actual A2687 power-curve call site passes `notificationSend = 0` on the
initial and retry requests. Combined with the already validated A2687 action
encoding convention, the evidence-backed one-parameter request layout is:

```text
A1 01 21          common action marker
A2 02 01 00       notificationSend = 0 (typed integer)
FE 04 <epoch LE>  current Unix timestamp
```

The WebBLE implementation now sends this read-only `0x020C` probe once after
the session startup sequence. It is intentionally not placed in the polling
loop because the `0x0A0C` response is packaged and may arrive in multiple
notifications. Until a real response is captured, the response TLVs are logged
verbatim rather than assigned speculative field names.

The official asynchronous report family also includes:

| Report | Opcode |
| --- | --- |
| device info / charge status | `0x0300` |
| device error code | `0x0301` |
| screen brightness or port status | `0x0302` |
| charge mode/current report | `0x0303` |
| screen-off time/error report | `0x0304` |
| clock screen saver/LED brightness | `0x0305` |
| OTA status | `0x0306` |
| port countdown | `0x0307` |
| port timer | `0x0308` |
| protective score/pinned-device report | `0x0309` |
| sleep mode | `0x030A` |
| language | `0x030B` |

The duplicate meanings occur because the SDK dispatches some identical opcodes
through different action metadata. The opcode alone is not always enough to
identify the payload layout.

### Implication for the existing polling code

The current WebBLE loop polls `0x0200` and `0x020A`. In the official enum,
`0x020A` is the Bluetooth-bind-success command, not the port-detail/history
command. WebBLE now sends `0x020C` once at startup and preserves the packaged
history response for mapping. The remaining telemetry work is to decode that
response and listen to the full `0x0300`-`0x030B` report family rather than
treating `0x020A` as the main realtime telemetry interface.

The old captured session key/nonce and captured `0x0021` public key have been
